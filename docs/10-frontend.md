# 10문서 — 프론트 연결 (커리큘럼 8단계)

출처: 아티팩트 "게시판 API 서버, 설계부터 배포까지" 8단계
<https://claude.ai/artifact/WffCicExjmUU5R7yfvba1H>

내가 만든 API 를 내가 만든 화면에 붙인다. **2단계 설계가 틀렸다면 여기서 드러난다** —
그것도 이 단계의 목적이다.

문서 번호(10)는 읽는 순서이고 커리큘럼 단계(8)와 다르다.

## 8.1 CORS — 이 구조에서는 왜 필요 없는가

브라우저는 자기가 받은 페이지와 같은 출처(`localhost:3001`)로만 요청한다.
Express(`localhost:4000`)는 BFF 가 서버에서 부르므로 브라우저가 교차 출처를 만들 일이 없다.

**그래도 무엇을 안 하고 있는지는 알고 넘어간다.** 페이지에서 직접 불러 봤다.

| 호출 | 결과 |
|---|---|
| `fetch('http://localhost:4000/posts')` | **`Failed to fetch`** — 막힌다 |
| `fetch('/api/graphql')` | `200` |

Express 응답에 `Access-Control-Allow-Origin` 헤더가 **0건**이다. BFF 를 걷어내고 브라우저가
Express 를 직접 부르게 하려면 그때 `cors` 미들웨어로 `origin`·`credentials`·허용 헤더를 정확히 열어야 한다.
`*` 로 열고 넘어가지 않는다 — 쿠키를 쓰면 `*` 는 아예 동작하지 않는다.

## 8.2 API 클라이언트 한 겹 — 그리고 401 을 되살리는 자리

`infrastructure/graphql/client.ts` 하나가 GraphQL 에러를 `DomainError` 로 바꾼다.
컴포넌트는 `error.code` 만 본다.

8단계에서 한 겹이 더 붙었다. **액세스 토큰은 15분이다.** 만료됐다고 곧바로 로그인 화면으로
보내면 15분마다 쫓겨난다.

```ts
if (err.code === "UNAUTHENTICATED" && (await refresh())) {
  return await send<T>(document, variables);   // 딱 한 번만 다시 시도한다
}
throw err;
```

**한 번만** 시도하는 것이 요점이다. 재발급이 또 401 을 주는 상황에서 다시 시도하면 무한히 돈다.

## 8.7 · 6.7 쿠키만 REST 로 뺀 이유

리프레시 토큰은 `httpOnly` 쿠키다. **쿠키는 HTTP 의 것이고 GraphQL 은 그것을 모른다.**
Yoga 응답에 `Set-Cookie` 를 끼워 넣을 수는 있지만 그러려면 리졸버가 응답 객체를 알아야 하고,
"스키마가 곧 계약" 이라는 성질이 깨진다.

그래서 로그인과 재발급만 `/api/auth/*` 로 내보냈다. 나머지는 전부 GraphQL 이다.

```
브라우저 ──▶ POST /api/auth/login  (Next Route Handler)
                  │ 쿠키를 그대로 넘김
                  ▼
             POST /auth/login       (Express)
                  │ Set-Cookie: refresh_token=…; Path=/auth
                  ▼
             Path 를 /api/auth 로 고쳐 브라우저에 심는다
```

`Path` 를 고치는 이유 — Express 가 정한 `Path=/auth` 를 그대로 두면 브라우저는 `/auth` 로 시작하는
요청에만 쿠키를 싣는다. 브라우저가 실제로 부르는 주소는 `/api/auth/refresh` 라서 안 실린다.

### 확인한 것

| 무엇 | 결과 |
|---|---|
| 로그인이 심는 쿠키 | `HttpOnly; SameSite=Strict; Path=/api/auth; Max-Age=1209600` |
| 쿠키로 재발급 | `200`, 새 액세스 토큰이 `/me` 에서 통한다 |
| 쿠키 없이 재발급 | `401` |
| 액세스 토큰을 쿠키에 넣어 재발급 | `401` (`typ` 검사가 막는다) |
| 2초 뒤 재발급 | 쿠키 값이 바뀌고 `iat`·`exp` 가 각각 +2초 — 회전한다 |
| **옛 리프레시 토큰으로 다시 재발급** | **`200`** |

마지막 줄이 6.7 에 적어 둔 한계다. **서버가 리프레시 토큰을 저장하지 않으므로 개별 취소가 안 된다.**
회전은 새 토큰을 주는 것일 뿐 옛 토큰을 무효로 만들지 못한다. 그러려면 발급한 토큰을
어딘가에 기록해야 하고, 그건 이번 범위 밖이다.

## 8.3 queryKey 에 필터를 넣는다

7단계에서 `sort`·`q`·`authorId` 가 생기면서 이 규칙이 **실제로 필요해졌다.**
넣지 않으면 조건이 다른 결과가 같은 자리를 덮어쓴다.

검색·정렬을 오가며 캐시 키를 찍어 봤다.

```
{"limit":20,"sort":"createdAt:desc"}
{"limit":20,"sort":"createdAt:desc","q":"argon2"}
{"limit":20,"sort":"createdAt:asc"}
```

셋이 서로 다른 캐시다. 검색어를 지우면 앞의 목록이 그대로 돌아온다 — 다시 받지 않는다.

## 8.4 staleTime

| 화면 | 값 | 왜 |
|---|---|---|
| 목록 | 60초 | 게시판 글은 1분 안에 거의 안 바뀐다 |
| 상세 | 15초 | 댓글이 달리기 때문에 목록보다 자주 바뀐다 |

기본값(0)으로 두지 않는다. 0 이면 포커스가 돌아올 때마다 다시 받는다.

## 8.5 낙관적 업데이트는 삭제 하나에만

삭제를 고른 이유가 있다. **결과를 미리 그릴 수 있고**(그 줄이 사라진다)
**되돌리는 것도 분명하다**(원래 자리에 다시 넣는다). 글 작성은 서버가 만든 id 가 있어야
화면을 제대로 그릴 수 있어 미리 그리기가 어렵다.

```ts
onMutate:  cancelQueries → 사본 저장 → 캐시에서 그 줄 제거
onError:   사본으로 되돌린다
onSettled: 성공이든 실패든 서버 상태를 다시 받아 맞춘다
```

`cancelQueries` 가 없으면 방금 지운 글을 담은 **예전 응답이 뒤늦게 도착해** 낙관적 업데이트를 덮어쓴다.
사본은 `getQueriesData` 로 전부 챙긴다 — 필터별로 캐시가 여러 벌이기 때문이다.

### 되돌리기를 어떻게 확인했나

**UI 가 남의 글 삭제 버튼을 숨겨서 정상 경로로는 실패를 만들 수 없다.**
`fetch` 를 가로채 삭제 요청에만 `FORBIDDEN` 을 돌려주는 방식으로 확인했다.

| 확인 | 결과 |
|---|---|
| 상세 화면 | "내 글만 삭제할 수 있습니다." 안내가 뜨고 **페이지에 머문다**(403 은 로그인 화면으로 보내지 않는다) |
| 목록으로 돌아가면 | 글이 **그대로 남아 있다** — 되돌려졌다 |

## 8.6 무한스크롤

`IntersectionObserver` 로 센티넬이 화면에 들어오면 다음 장을 부른다.
`rootMargin: "400px"` 으로 바닥에 닿기 전에 미리 부른다.

`getNextPageParam` 이 서버의 `pageInfo.nextCursor` 를 **그대로** 받는다.
2단계에서 목록 응답을 `{ items, pageInfo }` 로 정해 둔 값이 여기서 돌아왔다.

### 처음에 안 붙었다 — 그리고 두 번째 원인은 환경이었다

**첫 번째는 진짜 결함이었다.** 옵저버를 `useEffect` 로 한 번만 만들었는데,
그 시점에는 목록이 로딩 중이라 감시할 요소가 없었다. 나중에 요소가 붙어도 effect 는 다시 돌지 않는다.
**콜백 ref** 로 바꿨다 — 요소가 붙고 떨어질 때마다 불린다.

**두 번째는 환경이었다.** 고친 뒤에도 안 붙길래 같은 노드에 옵저버를 직접 붙여 봤더니 그것도 타임아웃이었다.
검증에 쓴 탭이 `visibilityState: hidden` 이라 **브라우저가 렌더링 단계를 돌리지 않고,
`IntersectionObserver` 콜백도 전달되지 않는다.**

그래서 배선은 데이터 층에서 확인했다. 센티넬이 부르는 것과 같은 함수를 캐시에서 직접 불렀다.

| 무엇 | 결과 |
|---|---|
| `fetchNextPage()` 두 번 | 항목 **20 → 60**, 캐시된 페이지 3 |
| `hasNext` | `true` |

**옵저버의 실제 발동은 확인하지 못했다.** 사람이 보는 탭에서 스크롤해 봐야 한다.

## 8.7 인증 상태 — 가드보다 먼저 걸리는 것이 있다

401 은 로그인 화면으로, 403 은 보내지 않는다. 여기까지는 계획대로였다.

**그런데 `useAuthGuard` 의 리다이렉트는 거의 타지 않는다.** 액세스 토큰이 만료되면
`me` 조회가 먼저 401 을 맞고, 화면이 "로그인해야 합니다" 안내로 바뀌기 때문이다.
가드가 도는 자리는 "`me` 는 아직 살아 있는데 변경 요청만 401" 이라는 좁은 창뿐이다.

그래서 **돌아올 자리를 실어 주는 일을 그 안내의 링크가 하게 했다.**

```
/login?returnTo=%2Fposts%2Fnew
```

`LoginForm` 은 `returnTo` 가 `/` 로 시작하는 내부 경로일 때만 받는다.
`returnTo=https://남의사이트` 를 그대로 믿으면 로그인 직후 그리로 보내진다(열린 리다이렉트).

### 로그아웃한 사람에게 글쓰기 폼이 보였다

`useMe` 는 토큰이 없으면 `enabled: false` 라 쿼리가 **영영 `pending`** 이다.
`isPending` 으로 "아직 모른다" 를 판단하던 화면은 로그아웃한 사람에게 폼을 그렸다.

토큰이 없다는 것은 그 자체로 답이다. `useViewer` 가 그 판단을 맡는다.

```ts
if (!hasToken) return { me: undefined, resolved: true };
return { me: query.data, resolved: !query.isPending };
```

- [x] 새 글을 쓰면 목록이 새로고침 없이 스스로 갱신된다 (`invalidateQueries`)
- [x] 토큰을 지우고 글을 쓰려 하면 로그인 화면으로 간다. 남의 글 수정은 로그인 화면이 아니라 권한 안내가 뜬다
- [~] 목록을 끝까지 스크롤하면 다음 페이지가 이어 붙고, 마지막에서 멈춘다
      — **데이터 층까지 확인했고 옵저버 발동은 확인하지 못했다**(위 8.6)

## 겪은 것

**검사 스크립트가 세 번 헛다리를 짚게 했다.** 6단계에서 헤더가 바뀌었는데 5단계 게이트가
`x-user-id` 를 그대로 쓰고 있어 7건이 실패했고, 고친 뒤에도 실패했다 —
가입 응답에는 토큰이 없어서(6단계부터) `$U` 에 유저 id 가 들어가 있었다.
**단계가 바뀌면 옛 검사 스크립트도 같이 옮겨야 한다.**

## 남은 것

- 옵저버 발동을 사람이 보는 탭에서 확인해야 한다.
- 댓글 "더 보기" 가 아직 없다. 상세는 첫 20개만 보여 주고 안내 문구만 뜬다.
- 글 수정 화면이 없다. `PATCH` 는 서버·BFF·유스케이스까지 다 있고 화면만 없다.
- 낙관적 업데이트는 삭제 하나뿐이다. 댓글 작성에도 붙일 수 있지만 id 를 서버가 만든다.
