## 6.1 비밀번호 — 왜 SHA-256 으로는 안 되는가

`SHA-256` 은 **빠르라고** 만든 함수다. GPU 한 장이 초당 수십억 번을 돌린다.
사람이 고르는 짧은 문자열은 흔한 후보 목록을 전부 돌려 보면 금방 맞는다.
같은 입력이 언제나 같은 해시라서 미리 계산해 둔 표(레인보우 테이블)를 조회하면 되고,
유출된 목록에서 같은 값이 겹치면 같은 비밀번호라는 것까지 드러난다.

`argon2` 는 반대다. **느리고 메모리를 많이 쓰라고** 만들었다.
이 라이브러리의 기본값으로 만든 해시는 이렇게 생겼다.

```
$argon2id$v=19$m=65536,p=4,t=3$<salt>$<hash>      (전체 97자)
```

한 번 계산에 64MiB(`m=65536`)가 필요하니 GPU 로 수천 개를 동시에 돌리기 어렵다.
salt 는 라이브러리가 넣어 준다 — 그래서 **같은 비밀번호라도 해시가 매번 다르고** 표가 쓸모없어진다.
파라미터가 문자열에 함께 들어 있어서, 나중에 비용을 올려도 옛 해시를 그대로 검증할 수 있다.

### 컬럼 이름도 같이 옮겼다

`password` 라는 이름의 컬럼에 해시가 들어 있으면 다음 사람이 평문인 줄 알고 비교한다.
그런데 `prisma migrate dev` 가 자동으로 만든 SQL 은 이랬다.

```
You are about to drop the column `password` on the `users` table,
which still contains 2 non-null values.
```

**이름만 바꾸는 일이 지우고 새로 만들기가 된다.** 그래서 마이그레이션 SQL 을 손으로 썼다.

```sql
ALTER TABLE "users" RENAME COLUMN "password" TO "passwordHash";
```

4단계 게이트가 "생성된 SQL 을 읽고 무슨 문장인지 말할 수 있다" 를 요구한 이유가 여기서 드러난다.
읽지 않았으면 데이터를 지웠을 것이다.

## 6.2 로그인 실패를 뭉개는 것만으로는 모자랐다

없는 이메일과 틀린 비밀번호를 구분하지 않고 `401` 하나로 답한다. 여기까지는 5단계에도 있었다.
6단계에서 하나가 더 필요해졌다 — **없는 이메일일 때 해시 검증을 건너뛰면 응답이 눈에 띄게 빨라진다.**
argon2 는 일부러 느리게 만든 함수라 그 차이가 크다. 시간만 재도 가입 여부를 알 수 있다.

그래서 유저가 없을 때도 더미 해시로 `verify` 를 한 번 돌린다. 결과는 버린다.

## 6.3 토큰은 암호화된 것이 아니다

페이로드에 `sub`(유저 id)와 `exp` 만 넣는다. 발급된 토큰을 열어 보면 이렇다.

```
키:        exp, iat, sub, typ
이메일:    0건
길이:      192자 (점 2개로 나뉜 세 조각)
```

**서명된 것이지 암호화된 것이 아니다.** 가운데 조각은 base64url 일 뿐이라 누구나 읽는다.
jwt.io 에 붙여 넣으면 그대로 보인다. 그래서 이메일·닉네임·권한을 넣지 않는다.

`typ` 를 넣은 것은 리프레시 토큰으로 API 를 부르지 못하게 막기 위해서다.
검증할 때 알고리즘도 값으로 못 박는다 — 토큰이 말하는 `alg` 를 그대로 믿으면
`alg: "none"` 이나 키 바꿔치기가 통한다.

## 6.4 이번에는 라우터가 한 줄도 안 바뀌었다

4단계에서는 "저장소만 바꾸면 라우터는 그대로" 라는 약속이 깨졌다. 조회가 동기에서 비동기가 되면서
호출하는 쪽이 전부 바뀌었다.

**6단계에서는 지켜졌다.** 인증 방식을 통째로 갈았는데 고친 파일은 `middleware/currentUser.ts` 하나다.
`routes/posts.ts` 와 `routes/comments.ts` 는 한 줄도 바뀌지 않았다.
헤더 이름도 토큰 형식도 그 파일 밖으로 새어 나가지 않게 해 두었기 때문이다.

차이는 **경계의 모양을 처음부터 맞춰 두었는지**에 있었다. 라우터가 아는 것은 `req.user.id` 하나뿐이고,
그 값이 어디서 오는지는 모른다.

## 6.5 · 6.6 401 과 403, 그리고 소유권

`401` 은 "누군지 모름", `403` 은 "누군지는 아는데 권한이 없음" 이다.
섞어 쓰면 프론트가 로그인 화면으로 보낼지 판단하지 못한다 — `403` 은 다시 로그인해도 해결되지 않는다.

소유권 검사는 **핸들러 안에 둔다.** 미들웨어로 뺄 수도 있었지만 그러려면 미들웨어가
"이 요청이 다루는 리소스" 를 먼저 읽어야 하고, 그러면 핸들러가 같은 것을 또 읽거나
미들웨어가 읽은 것을 전달하는 장치가 필요해진다. 검사가 세 곳(글 수정·글 삭제·댓글 삭제)뿐이라
핸들러에 두는 쪽이 짧다. 세 곳 모두 **존재 검사 → 소유권 검사** 순서를 지킨다.

## 6.7 리프레시 토큰

| | 액세스 | 리프레시 |
|---|---|---|
| 형식 | JWT | JWT |
| 수명 | 15분 | 14일 |
| 사는 곳 | 클라이언트가 정한다(지금은 `localStorage`) | `httpOnly` 쿠키 |
| 쓰이는 곳 | 모든 API 요청 | `POST /auth/refresh` 만 |

`localStorage` 는 페이지에 끼어든 스크립트가 읽어 간다(XSS). `httpOnly` 쿠키는 자바스크립트가
아예 읽지 못하므로 그 경로가 막힌다. 대신 쿠키는 자동으로 실려 가므로 CSRF 를 따로 막아야 하고,
`sameSite: "strict"` 가 그 몫이다.

액세스 토큰을 15분으로 짧게 두는 이유도 같다. 어차피 자바스크립트가 닿는 곳에 두게 되는데,
새어 나가도 15분 뒤에는 쓸모가 없다.

**한계를 적어 둔다.** 서버가 리프레시 토큰을 저장하지 않으므로 **개별 취소가 안 된다.**
"모든 기기에서 로그아웃" 같은 기능을 만들려면 발급한 토큰을 어딘가에 기록해야 한다.
이번 범위 밖이다(`docs/01-domain.md` 의 "안 만들 것" 과 같은 성격의 선택이다).

## 검사를 만들다 겪은 것

**JWT 서명의 마지막 글자를 바꿔도 검증이 통과했다.** 처음에는 서버 결함인 줄 알았다.
HS256 서명은 32바이트이고 base64url 로 43자가 되는데, **마지막 글자는 실제 비트를 2개만 담는다.**
나머지 4비트는 패딩이라 여러 글자가 같은 바이트로 디코드된다.

서버는 정상이고 검사가 틀린 것이었다. 남의 키로 서명한 토큰과 서명을 잘라낸 토큰으로 바꾸니
둘 다 `401` 이 나왔다. **검사가 실패를 보고했다고 코드가 틀린 것은 아니다.**

## 남은 것

- **BFF 를 거치는 리프레시 흐름을 아직 잇지 않았다.** 리프레시 쿠키는 Express 가 심는데,
  브라우저는 Next 와 이야기한다. 중간의 BFF 가 `Set-Cookie` 를 옮겨 주어야 하고,
  그 배선은 8단계(프론트 연결)의 일이다. 지금 브라우저는 액세스 토큰이 만료되면 다시 로그인해야 한다.
- 6단계 전에 만든 계정은 쓸 수 없다. 평문을 해시로 바꾸는 것은 SQL 이 할 수 없어서
  학습용 데이터는 다시 만들었다. 실제 서비스라면 "다음 로그인 때 해시로 교체" 같은 이행 기간을 둔다.
