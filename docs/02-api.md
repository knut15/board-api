## 2.1 URL 규칙

1. **복수 명사, 소문자.** `/posts`, `/comments`. `/Post`, `/post` 아니다.
2. **동사를 넣지 않는다.** `/posts/create`, `/posts/:id/delete` 는 쓰지 않는다. 행위는 메서드가 표현한다.
3. **중첩은 한 단계까지.** `/posts/:id/comments` 는 되고 `/users/:id/posts/:id/comments` 는 안 된다.
   두 단계가 필요해 보이면 쿼리 파라미터로 푼다 — `/posts?authorId=...`.
4. **행위 경로는 `/auth/*` 에만 둔다.** 가입·로그인은 리소스가 아니다. 이 예외를 여기에만 두고 늘리지 않는다.
5. **id 는 경로에, 그 밖의 조건은 쿼리에.** 정렬·필터·페이지는 전부 쿼리 파라미터다.

## 2.2 엔드포인트 12개

| # | 메서드 | 경로 | 하는 일 | 인증 | 성공 | 실패 |
|---|---|---|---|---|---|---|
| 1 | POST | `/auth/signup` | 가입 | — | `201` | `400` `409` `422` |
| 2 | POST | `/auth/login` | 로그인, 토큰 발급 | — | `200` | `400` `401` |
| 3 | GET | `/me` | 내 정보 | 필요 | `200` | `401` |
| 4 | GET | `/posts` | 글 목록 (정렬·필터·페이지) | — | `200` | `400` |
| 5 | POST | `/posts` | 글 작성 | 필요 | `201` | `400` `401` `422` |
| 6 | GET | `/posts/:id` | 글 상세 (작성자 + 댓글 첫 페이지) | — | `200` | `404` |
| 7 | PATCH | `/posts/:id` | 글 수정 | 소유자 | `200` | `400` `401` `403` `404` `422` |
| 8 | DELETE | `/posts/:id` | 글 삭제 | 소유자 | `204` | `401` `403` `404` |
| 9 | GET | `/posts/:id/comments` | 댓글 목록 | — | `200` | `400` `404` |
| 10 | POST | `/posts/:id/comments` | 댓글 작성 | 필요 | `201` | `400` `401` `404` `422` |
| 11 | DELETE | `/comments/:id` | 댓글 삭제 | 소유자 | `204` | `401` `403` `404` |
| 12 | POST | `/auth/refresh` | 액세스 토큰 재발급 | 쿠키 | `200` | `401` |
| 13 | POST | `/auth/logout` | 로그아웃 | 없음 | `204` | — |

**12번은 6.7 에서 늘어났다.** 2단계에서 11개로 확정했는데, 리프레시 토큰을 쓰기로 하면
그것을 액세스 토큰으로 바꿀 자리가 있어야 한다. 표가 늘어난 것을 숨기지 않고 여기에 적는다 —
명세를 고치지 않고 코드만 늘리면 다음 사람이 표를 믿지 못하게 된다.

메서드 배정 규칙:

- 조회 `GET`, 생성 `POST`, **부분** 수정 `PATCH`, 삭제 `DELETE`.
- `PUT` 은 쓰지 않는다. 리소스를 통째로 교체하는 자리가 이번 프로젝트에 없다.
  글 수정은 제목만 또는 본문만 보내는 것이 정상이므로 `PATCH` 다.

### 인증은 어떻게 싣는가

`Authorization: Bearer <액세스 토큰>` 헤더다. 토큰은 `POST /auth/login` 이 준다.

| | |
|---|---|
| 액세스 토큰 | JWT, 15분. 페이로드에 `sub`(유저 id)와 `exp` 만 있다 |
| 리프레시 토큰 | `httpOnly` 쿠키(`refresh_token`), 14일. 자바스크립트가 읽지 못한다 |

**토큰은 서명된 것이지 암호화된 것이 아니다.** 누구나 페이로드를 읽을 수 있으므로
이메일·닉네임·권한을 넣지 않는다.

액세스 토큰이 만료되면 `401` 이 온다. 그때 `POST /auth/refresh` 를 부르면
쿠키에 실려 간 리프레시 토큰으로 새 액세스 토큰을 받는다. 리프레시 토큰도 함께 갈아 끼운다.

5단계까지는 `x-user-id` 헤더에 유저 id 를 적어 보내는 흉내였다. 6.4 에서 사라졌다.

### GET /posts 의 쿼리 파라미터

7단계에서 구현하지만 이름은 여기서 고정한다. 8.3 의 `queryKey` 가 이 이름을 그대로 쓴다.

| 이름 | 타입 | 기본값 | 비고 |
|---|---|---|---|
| `limit` | int 1–50 | `20` | 범위 밖은 `400` |
| `cursor` | string | 없음 | 마지막 항목의 id. 무한스크롤용 |
| `sort` | enum | `createdAt:desc` | `createdAt:desc` · `createdAt:asc` 둘뿐. 그 밖은 `400` |
| `q` | string 1–100 | 없음 | 제목 검색(대소문자 무시) |
| `authorId` | uuid | 없음 | 형식이 uuid 가 아니면 `400` |

**모르는 파라미터를 보내면 `400`** 이다(7.4). 조용히 무시하면 오타가 "필터가 안 먹네" 로 나타난다.

`page` / `offset` 은 두지 않는다. 7.2 에서 offset 방식을 실습하되 최종 API 는 커서 하나로 간다 —
두 방식을 동시에 열어 두면 8.6 의 `getNextPageParam` 이 무엇을 기준으로 삼는지 흐려진다.

## 2.3 상태 코드 규약

| 코드 | 이름 | 언제 |
|---|---|---|
| `200` | OK | 조회 성공. 수정 성공 중 바뀐 결과를 돌려줄 때 |
| `201` | Created | 생성 성공. **GET 으로 가져올 수 있는 단건 경로가 있을 때만** `Location` 헤더를 넣는다 — `POST /posts` 만 해당한다. 가입·댓글 작성은 그 경로가 11개 안에 없어 붙이지 않는다 |
| `204` | No Content | 삭제 성공. 바디를 비운다. 빈 객체 `{}` 를 보내지 않는다 |
| `400` | Bad Request | 형식이 틀림. JSON 파싱 실패, 타입 불일치, 없는 정렬 키 |
| `401` | Unauthorized | 누군지 모름. 토큰이 없거나 만료됐거나 서명이 안 맞음 |
| `403` | Forbidden | 누군지는 아는데 권한이 없음. 남의 글을 지우려 할 때 |
| `404` | Not Found | 그런 리소스가 없음 |
| `409` | Conflict | 지금 상태와 충돌. 이미 가입된 이메일 |
| `422` | Unprocessable | 형식은 맞지만 값이 규칙 위반. 제목 200자 초과 |
| `500` | Internal | 서버 잘못. 내부 사정을 응답에 담지 않는다 |

### 400 과 422 를 가르는 선

판단이 갈리는 자리라 못 박는다. 규칙이 둘이다.

**1. 쿼리 파라미터와 경로 파라미터의 문제는 언제나 `400`.**
주소에 실려 오는 값이라 형식의 문제로 본다. `?limit=999` 처럼 값이 범위를 벗어난 것도
`400` 이다 — 주소가 잘못 만들어진 것이기 때문이다.

**2. 본문만 형식(`400`)과 값(`422`)을 가른다.** 판정은 zod 이슈 코드로 기계적으로 한다.

| zod 이슈 (zod 4) | 코드 | 예 |
|---|---|---|
| `invalid_type` | `400` | `title` 에 숫자, 필드 누락 |
| `invalid_value` | `400` | enum 에 없는 값 |
| `invalid_format` | `400` | uuid·email 형식이 아님 |
| `unrecognized_keys` | `400` | 스키마에 없는 필드 |
| `too_small` · `too_big` | `422` | 제목 0자 / 201자 |
| `custom` (refine) | `422` | PATCH 에 고칠 필드가 하나도 없음 |

한 요청에 둘이 섞이면 **`400` 이 이긴다.** 형식부터 틀린 것을 값 문제로 보고할 이유가 없다.
이 판정은 `server/src/middleware/validate.ts` 한 곳에서만 한다.

**JSON 자체가 깨진 경우**도 `400` 이다. `express.json()` 이 던지는 파싱 에러를
에러 핸들러가 받아 옮긴다 — 라이브러리 메시지에는 깨진 본문 일부가 들어 있어 그대로 내보내지 않는다.

## 2.4 바디 형태

예외를 하나도 두지 않는다. 8.2 의 API 클라이언트가 이 세 형태만 해석하면 되게 한다.

### 단건 — 객체 그대로 (봉투 없음)

```json
// GET /posts/:id
{
  "id": "9f1c…",
  "title": "첫 글",
  "body": "본문",
  "author": { "id": "4a…", "nickname": "kim" },
  "commentCount": 3,
  "comments": {
    "items": [
      { "id": "c1…", "body": "첫 댓글",
        "author": { "id": "7d…", "nickname": "lee" },
        "createdAt": "2026-09-15T02:20:00.000Z" }
    ],
    "pageInfo": { "nextCursor": "c9…", "hasNext": true }
  },
  "createdAt": "2026-09-15T02:11:40.000Z",
  "updatedAt": "2026-09-15T02:11:40.000Z"
}
```

`{ "data": … }` 같은 봉투를 씌우지 않는다. 목록만 봉투가 있고 단건은 없다.

### 목록 — `{ items, pageInfo }`

```json
// GET /posts?limit=20&cursor=…
{
  "items": [
    { "id": "9f1c…", "title": "첫 글",
      "author": { "id": "4a…", "nickname": "kim" },
      "commentCount": 3,
      "createdAt": "2026-09-15T02:11:40.000Z" }
  ],
  "pageInfo": { "nextCursor": "7b2e…", "hasNext": true }
}
```

목록 항목에 `body` 를 넣지 않는다. 상세에서만 준다.
마지막 페이지는 `{ "nextCursor": null, "hasNext": false }`.

### 에러 — 모든 4xx·5xx 가 이 형태 하나

```json
{
  "error": {
    "code": "POST_NOT_FOUND",
    "message": "글을 찾을 수 없습니다.",
    "details": null
  }
}
```

- `message` 는 사람이 읽는 것이다. **프론트는 `message` 가 아니라 `code` 로 분기한다.**
- `details` 는 검증 실패일 때만 채운다: `[{ "path": "title", "rule": "too_big" }]`.
- 스택 트레이스, 테이블명, 컬럼명, Prisma 에러 코드 원문을 절대 담지 않는다(5.7).

### 에러 코드 목록

5.4 에서 상수 파일로 옮긴다. 여기 없는 코드를 코드베이스에서 만들지 않는다.

| `code` | HTTP | 언제 |
|---|---|---|
| `VALIDATION_FAILED` | `400` / `422` | 2.3 의 선대로 |
| `EMAIL_ALREADY_EXISTS` | `409` | 가입 시 이메일 중복 |
| `INVALID_CREDENTIALS` | `401` | 로그인 실패 (이메일 없음과 비밀번호 틀림을 구분하지 않는다) |
| `UNAUTHENTICATED` | `401` | 토큰 없음 · 서명 불일치 · 만료 |
| `FORBIDDEN` | `403` | 남의 리소스 |
| `POST_NOT_FOUND` | `404` | 그 글이 없음 |
| `COMMENT_NOT_FOUND` | `404` | 그 댓글이 없음 |
| `ROUTE_NOT_FOUND` | `404` | 경로 자체가 없음 |
| `INTERNAL_ERROR` | `500` | 그 밖 전부 |

## 2.5 안전성과 멱등성

| 메서드 | 안전(아무것도 안 바꿈) | 멱등(여러 번 = 한 번) | 확인 |
|---|---|---|---|
| `GET` × 4 | 예 | 예 | 4개 전부 DB 를 쓰지 않는다 |
| `POST` × 4 | 아니오 | 아니오 | 두 번 누르면 두 개 생긴다. 중복 방지는 프론트가 막는다 |
| `PATCH` × 1 | 아니오 | 예 | 같은 바디를 두 번 보내면 결과가 같다 |
| `DELETE` × 2 | 아니오 | 예 | 서버 상태는 같다. 응답 코드는 아래 |

### 정한 것 — 같은 DELETE 를 두 번 보내면 두 번째는 `404`

`204` 로 두는 선택지도 있었다. `404` 로 간 이유는 **없는 리소스에 대한 응답을 메서드별로
다르게 만들지 않기 위해서다.** `GET /posts/:id`, `PATCH /posts/:id`, `DELETE /posts/:id` 가
없는 id 에 대해 모두 `404` + `POST_NOT_FOUND` 로 같으면, 8.2 의 클라이언트가 분기를 하나만 갖는다.

HTTP 의 멱등성은 *서버 상태*가 같다는 뜻이지 응답 코드가 같다는 뜻이 아니므로 규약 위반이 아니다.
8.5 의 낙관적 삭제에서 `404` 는 "이미 없음" 이므로 롤백하지 않고 성공으로 친다.

### 정한 것 — 없는 글을 남이 지우려 하면 `403` 이 아니라 `404`

**존재 검사가 권한 검사보다 먼저다.** 없는 글에는 소유자가 없으므로 `403` 을 줄 근거가 없다.

존재하는 남의 글에 대해서는 `403` 을 준다. 이것으로 "그 글이 있다" 는 사실이 새어 나가지만,
`GET /posts/:id` 가 인증 없이 열려 있어 애초에 공개 정보다. 글이 비공개가 되는 날
(안 만들 것 목록에 없음 → 만들게 되면) 이 결정을 다시 본다. 6.6 에서 이대로 구현한다.

## 2.6 프론트 시점 리뷰 — 화면당 호출 횟수

| 화면 | 호출 | 횟수 |
|---|---|---|
| 글 목록 | `GET /posts` | 1 |
| 글 상세 | `GET /posts/:id` (작성자 + 댓글 첫 20개 포함) | 1 |
| 댓글 더 보기 | `GET /posts/:id/comments?cursor=…` | +1 (사용자가 누를 때만) |
| 로그인 | `POST /auth/login` | 1 |
| 가입 | `POST /auth/signup` | 1 |
| 글 쓰기 | `POST /posts` | 1 |
| 내 정보 | `GET /me` | 1 |

**첫 화면을 그리는 데 두 번 호출하는 화면이 없다.** 이 게이트를 맞추려고
`GET /posts/:id` 에 작성자와 댓글 첫 페이지를 같이 담았다(2.4 의 단건 예시).
`GET /posts/:id/comments` 는 사라지지 않는다 — 댓글 페이지네이션에 쓴다.

목록에 `commentCount` 를 넣은 것도 같은 이유다. 이것 때문에 7.7 에서 `_count` 로
N+1 을 없애는 작업이 필요해진다 — 설계가 성능 과제를 만든 자리이고, 의도한 것이다.

- [x] 목록 응답과 에러 응답 형태가 예시 JSON 으로 고정돼 있다
- [x] 화면별 호출 횟수를 세었고, 두 번 이상 필요한 화면이 없다
