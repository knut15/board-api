## 9.1 환경변수 — 틀리면 뜨지 않는다

`src/env.ts` 하나가 읽고 **형식까지** 검증한다. 다른 모듈은 `process.env` 를 직접 읽지 않고
여기서 내보내는 `env` 를 쓴다.

```ts
export const env = parsed.data;   // 타입이 붙은 값
```

**이 구조가 6단계에서 겪은 문제를 구조적으로 없앴다.** 그때는 `.env` 읽기를 `store/prisma.ts` 안에
두었더니 `auth/tokens.ts` 가 먼저 로드되면서 `JWT_SECRET` 을 못 찾고 서버가 죽었다.
지금은 `env` 를 import 하는 것이 곧 "검증이 끝난 뒤에 쓰겠다" 는 선언이라 순서가 저절로 맞는다.

| 검사하는 것 | 규칙 |
|---|---|
| `DATABASE_URL` | URL 형식 |
| `JWT_SECRET` | **32자 이상** — 짧은 키는 무차별 대입으로 뚫린다 |
| `PORT` | 1–65535 정수, 기본 4000 |
| `NODE_ENV` | `development` · `test` · `production` |
| `LOG_LEVEL` | pino 의 여섯 단계, 기본 `info` |
| `CORS_ORIGIN` | 선택. BFF 를 걷어내는 날 필요해진다(8.1) |

### 실제로 어긋났을 때

```
환경변수가 올바르지 않습니다:
  DATABASE_URL — postgresql://… 형태의 주소여야 합니다.
  JWT_SECRET — 반드시 있어야 합니다.
```

**한 줄에 하나씩, 무엇이 왜 틀렸는지 적는다.** `invalid env` 한 줄만 찍으면 배포 로그를 보는
사람이 어느 값을 고쳐야 하는지 모른다. 종료 코드는 `1` 이다 — 플랫폼이 실패로 인식해야 한다.

`.env` 파일은 **있으면 읽고 없으면 넘어간다.** 배포 환경에서는 플랫폼이 직접 주입하므로 없는 것이 정상이다.

## 9.2 개발 실행과 운영 실행을 가른다

| | 명령 | 무엇이 도나 |
|---|---|---|
| 개발 | `pnpm dev` | `tsx watch src/server.ts` — 고치면 다시 뜬다 |
| 빌드 | `pnpm build` | `prisma generate && tsc` → `dist/` |
| 운영 | `pnpm start` | `node dist/server.js` — **TypeScript 도구가 하나도 끼지 않는다** |

`tsx`·`typescript`·`prisma` CLI 는 전부 `devDependencies` 다. 운영 실행 경로에 섞이지 않는다.

`dist` 에 JS 21개가 나왔고 그것만으로 떴다. **`import "./app.js"` 처럼 `.js` 확장자를 붙여 둔 값이
여기서 돌아온다** — `NodeNext` 는 확장자를 생략한 상대 import 를 해석하지 않으므로,
3단계에서 그렇게 쓰지 않았으면 빌드 결과가 돌지 않았을 것이다.

## 9.5 로그 — `console.log` 로는 배포 뒤에 못 찾는다

`pino` 로 JSON 한 줄씩 남긴다. 플랫폼의 로그 검색은 문자열이 아니라 **필드**를 건다.

```json
{"level":30,"time":1790061453097,"reqId":"dd5ce7c6-…","method":"GET","url":"/health","status":200,"ms":4.3,"msg":"request"}
```

### 요청 id 가 필요한 이유

배포된 서버는 요청을 동시에 여러 개 처리한다. id 가 없으면 로그가 뒤섞여 **어느 줄이 어느 요청의
것인지 알 수 없다.** `x-request-id` 헤더가 오면 그 값을 쓰고, 없으면 만들어 응답 헤더로 돌려준다 —
프록시 로그와 우리 로그를 같은 id 로 이을 수 있고, 사용자가 "이 요청이 실패했다" 고 신고할 수도 있다.

자식 로거(`logger.child({ reqId })`)를 `req.log` 에 붙여 두면 그 요청에서 찍는 모든 줄에 id 가 자동으로 붙는다.
에러 핸들러도 `req.log.error` 를 쓴다.

### 비밀이 로그에 실리는 사고를 구조적으로 막는다

`redact` 로 경로를 정해 두면 **어느 핸들러가 무엇을 찍든** 그 값은 `[Redacted]` 가 된다.

```
authorization · cookie · password · passwordHash · token
```

직접 찍어 확인했다 — 다섯 값이 전부 마스킹되고 원문 노출 **0건**.

```json
{"req":{"headers":{"authorization":"[Redacted]","cookie":"[Redacted]"}},"body":{"password":"[Redacted]"},…}
```

`pino-pretty` 로 개발에서 읽기 좋게 꾸밀 수 있지만 넣지 않았다. **개발에서 보는 모양과 운영에서
보는 모양이 같은 편이** "로그에 이 필드가 없네" 를 일찍 알아차리게 한다.

## 9.6 내려갈 때 끊지 않는다

배포 플랫폼은 서버를 내릴 때 `SIGTERM` 을 보내고 잠시 기다린다. 그 사이에 할 일이 셋이다.

1. 새 요청을 받지 않는다 (`server.close` 가 리스너를 닫는다)
2. **진행 중인 요청을 끝낸다** (close 의 콜백이 그때 불린다)
3. DB 연결을 닫는다

이걸 하지 않으면 배포할 때마다 처리 중이던 요청이 끊긴다. 사용자 쪽에서는
**"가끔 저장이 안 된다"** 로 보인다 — 재현이 안 돼서 찾기 어려운 종류의 문제다.

### 실제로 재 봤다

동시 요청 40개를 쏘고 곧바로 `SIGTERM` 을 보냈다.

| | 결과 |
|---|---|
| 이미 처리 중이던 요청 | **3건이 신호 이후에 200 으로 끝났다** (41.9 · 41.2 · **140.4** ms) |
| 그 뒤 | `closed` 로그 → 프로세스 종료 → 포트 반환 |
| 아직 연결되지 않은 37건 | 거부 — 의도한 동작이다 |

140.4ms 짜리가 증거다. 신호를 받은 뒤에도 하던 일을 끝냈다.

**10초 안에 못 끝내면 강제로 나간다.** 영영 안 닫히는 연결 하나 때문에 배포가 멈추는 것이 더 나쁘다.

`/health` 는 3.2 에서 만든 것을 그대로 쓴다. 플랫폼의 헬스체크에 물리는 일만 남았다.

## 배포하기 전에 정해야 할 것

### 릴리스 커맨드

```
prisma migrate deploy && node dist/server.js
```

**`migrate dev` 를 운영에서 절대 쓰지 않는다.** 그 명령은 스키마를 맞추려고 데이터를 지울 수 있고,
비대화식 환경에서는 아예 멈춘다 — 6단계에서 `password` → `passwordHash` 를 바꿀 때 실제로 겪었다.
`migrate deploy` 는 이미 만들어진 마이그레이션만 순서대로 적용한다.

### 두 서비스를 어떻게 잇는가

서버와 DB 가 한 프로젝트 안에 있어도 **주소는 환경변수로 주입받는다.** 로컬 `.env` 를 그대로
올리지 않는다 — 거기 적힌 `localhost:5432` 는 플랫폼 안에서 아무것도 가리키지 않는다.

### 클라이언트도 같이 올릴 것인가

Next.js 가 BFF 를 들고 있어서 **서버 두 개를 올려야 한다**(Express + Next).
Next 쪽에는 `BOARD_API_URL` 이 필요하고, 그 값이 플랫폼 안에서 Express 를 가리켜야 한다.
지금은 기본값 `http://localhost:4000` 이다.

## 운영에서 이미 걸린 것 하나

`server/compose.yaml` 에 `name:` 이 없어서 **디렉터리 이름 `server` 가 프로젝트 이름이 된다.**
컨테이너는 `server-db-1`, 볼륨은 `server_pgdata` 다.

`~/Workspace` 아래에 DB 정의를 `server/` 에 두는 레포가 또 있으면 **둘이 같은 컨테이너와 볼륨을
공유한다.** 한쪽에서 `up -d` 를 하면 다른 쪽 컨테이너가 재생성된다. Postgres 는 `PGDATA` 가 이미
초기화돼 있으면 `POSTGRES_USER`·`POSTGRES_DB` 를 조용히 무시하므로,
**컨테이너가 healthy 여도 안의 DB 는 남의 것일 수 있다.**

고치는 법은 한 줄이다.

```yaml
name: board-api
services:
  db: …
```

다만 프로젝트 이름이 바뀌면 컨테이너와 볼륨 이름도 바뀐다. 지금 볼륨(`server_pgdata`)은 남고
빈 볼륨(`board-api_pgdata`)이 새로 생긴다 — **DB 가 비어 보인다.** 이 레포의 데이터는 전부
시드라서 다시 넣으면 그만이지만(6초), 그 사실을 모르고 겪으면 당황한다.
