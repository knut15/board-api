# server/src/app.ts

> 커리큘럼 3.3 · 3.5 · 3.6 · 짝: `server/src/app.ts`

## 무엇을 하는 파일인가

요청 하나가 서버 안에서 지나가는 길을 정한다. `createApp()` 안의 줄 순서가 곧 그 길이라 줄을
위아래로 옮기면 동작이 바뀐다. 라우터를 어디에 붙일지, 안 걸린 요청과 에러를 누가 받을지가 있다.

## 코드를 따라 읽기

등록 순서만 추리면 이렇다. 요청은 위에서 아래로 흐르다가 누군가 응답하면 그 자리에서 멈춘다 —
**각 단계가 다음으로 넘길지(`next()`) 여기서 끝낼지(`res.json()`) 를 스스로 고른다.**

```ts
app.use(logger);                                         // 1
app.use(express.json());                                 // 2
app.use(currentUser);                                    // 3
app.get("/health", …);                                   // 4
app.use("/auth", authRouter);                            // 5
app.use("/posts/:postId/comments", postCommentsRouter);
app.use("/posts", postsRouter);
app.use((_req, res) => { fail(res, 404, "ROUTE_NOT_FOUND", …); });      // 6
app.use((err, _req, res, _next) => { … fail(res, 500, …); });           // 7
```

`logger` 가 가장 위인 이유는 뒤에서 무슨 일이 나도 요청이 들어온 사실은 남기기 위해서다. 2번
아래로 내리면 파싱 단계에서 죽은 요청이 로그에 안 찍힌다.

`express.json()` 은 요청 본문(바이트 덩어리)을 읽어 `req.body` 에 객체로 넣는 미들웨어다.
**이 줄을 지우면 `req.body` 가 `undefined` 가 된다** — Express 가 본문을 자동으로 읽어 주지
않기 때문이다. 프론트에서 `await res.json()` 을 직접 불러야 했던 것과 같다. 라우터들이
`req.body ?? {}` 로 받아 두었으니 서버가 죽지는 않고 `POST /auth/signup` 이 `400` +
`VALIDATION_FAILED` 로 답한다(`docs/02-api.md` 2.4). 파싱 대상은 `Content-Type:
application/json` 인 요청뿐이다 — 프론트가 헤더를 빼먹으면 라우터는 "값을 안 보냈다" 고 본다.

`currentUser` 는 요청자를 알아내 `req.user` 에 넣고, 못 알아내도 통과시킨다. 로그인 없이 볼 수
있는 엔드포인트가 있어서다. `401` 은 라우터마다 끼우는 `requireAuth` 가 낸다.

`app.use("/posts", postsRouter)` 는 **경로가 `/posts` 로 시작하는 요청 전부**를 라우터 안으로
들여보낸다. `/posts/abc/comments` 도 이 조건에 걸린다. 그런데 들어간 뒤 `postsRouter` 안에는
`/abc/comments` 에 맞는 라우트가 없고(`/:id` 는 한 칸만 먹는다), 라우터는 응답하지 않고
`next()` 로 요청을 돌려보낸다. 요청은 다음 마운트로 계속 흐른다. **접두사가 처음 맞는 라우터가
요청을 독점하지 않는다** — 3.3 에서 잡아야 할 그림이 이것이다. 댓글 라우터를 위에 둔 것은 그
사실에 기대지 않고 의도를 먼저 보이려는 것이고, `postsRouter` 에 `/:id/comments` 가 생기는 날
부터는 순서가 곧 결과다.

6번은 경로를 안 적은 `app.use` 라 **모든 요청에 맞는다.** 라우터 등록보다 위에 두면 첫 요청부터
전부 `404` 다. 여기까지 내려온 요청은 어느 라우터도 손들지 않은 요청이므로 "그런 경로가 없다"
가 맞는 답이고, 코드는 리소스가 없는 `POST_NOT_FOUND` 와 구분해 `ROUTE_NOT_FOUND` 다(2.4).

7번이 에러 핸들러인 것은 **인자가 4개**라서다. Express 는 등록된 함수의 인자 개수를 세어 3개면
보통 미들웨어, 4개면 에러 핸들러로 분류한다. 안 쓰는 `_next` 를 지우면 인자가 3개가 되고 그
순간 이 함수는 에러를 못 받는 평범한 미들웨어가 된다 — 쓰지 않는 인자가 문법이 아니라 신호다.

## 왜 이렇게 했는가

1. **미들웨어를 전역에 둘지 라우터마다 둘지.** `currentUser` 는 전역, `requireAuth` 는
   라우터별이다. 식별은 모든 요청에 필요하지만 강제는 일부에만 필요하다 — 합쳐 전역에 두면
   `GET /posts` 가 로그인을 요구하게 된다.
2. **404 를 한 곳에 모은 것.** 라우터마다 마지막에 적는 방법도 있다. 모으면 형태가 갈라지지
   않는 대신 "아래에 둬야 한다" 는 순서 규칙을 사람이 기억해야 한다 — 번호 주석이 그 몫이다.
3. **에러 핸들러를 미리 만들어 둔 것.** 3단계에는 던지는 곳이 없어 거의 안 불리지만 5단계에서
   이 자리가 응답 조립의 중심이 된다. 비워 두는 편이 나중에 순서를 다시 고민하는 것보다 싸다.

## 직접 해 볼 것

1. `app.use(express.json())` 을 주석 처리하고 `POST /auth/signup` 에 정상 바디를 보낸다 →
   응답이 `400` + `VALIDATION_FAILED` 로 바뀐다. 라우터는 한 줄도 안 고쳤는데 결과가 바뀐다.
2. 6번 404 미들웨어를 라우터 등록 **위로** 옮긴다 → `GET /health` 까지 포함해 모든 요청이
   `ROUTE_NOT_FOUND` 로 답하는 것을 확인하고 되돌린다.
3. 라우터 아무 곳에 `throw new Error("boom")` 을 넣고 호출한 뒤, 7번 핸들러의 `_next` 를 지워
   인자를 3개로 만들고 다시 호출한다 → 두 응답을 비교하면 Express 의 판별 기준이 드러난다.

## 다음 단계에서 어떻게 바뀌는가

5단계에서 7번 핸들러가 `AppError` 를 받아 상태 코드와 `code` 를 꺼내 쓰게 되고 라우터의
`fail()` 직접 호출이 사라진다(→ `respond.md`). 6.4 에서는 3번 `currentUser` 의 안쪽만 JWT
검증으로 바뀌며 줄 순서는 그대로다. 9.2 · 9.3 에서 CORS · helmet · rate limit 이 1번과 2번
사이로 들어오고, 9.5 에서 `logger` 가 pino 로 교체된다 — 자리는 둘 다 지금과 같다.
