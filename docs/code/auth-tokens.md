# server/src/auth/tokens.ts

> 커리큘럼 6.3 · 6.7 · 짝: `server/src/auth/tokens.ts`

## 무엇을 하는 파일인가

토큰을 **만들고 검증한다.** 5단계까지 "토큰" 은 유저 id 그 자체였다 — `x-user-id` 헤더에 남의
id 를 적어 보내면 그 사람이 됐다. 여기서 서명("이 문자열은 우리가 만들었다")과 만료("언제까지만
유효하다")가 붙는다. 리프레시 토큰을 쿠키에 실을 때 쓰는 이름과 옵션도 이 파일에 있다(6.7).

## 코드를 따라 읽기

### 서명 키가 없으면 시작하지 않는다

`process.env.JWT_SECRET` 이 비어 있으면 모듈을 평가하는 중에 그대로 던진다. 기본값을 몰래
넣어 두면 그 값으로 서명된 토큰이 운영에서도 통한다 — 공개된 코드에 적힌 키는 키가 아니다.
이 줄이 실제로 부팅을 막은 사건이 `docs/code/env.md` 에 있다.

### 알고리즘을 값으로 못 박는다

```ts
const ALG = "HS256";
.setProtectedHeader({ alg: ALG })                     // 만들 때
await jwtVerify(token, key, { algorithms: [ALG] });   // 검증할 때
```

**검증할 때 토큰이 말하는 `alg` 를 믿으면 안 된다.** 토큰 헤더는 공격자가 고쳐 보내는 값이다.
`alg: "none"` 으로 바꿔 서명 없이 통과시키거나, 비대칭 키를 쓰는 서버에서 공개키를 대칭키로
바꿔치기하는 공격이 여기서 나온다. `algorithms: [ALG]` 를 넘기면 그 목록 밖을 주장하는 토큰은 서명을 보기도 전에 떨어진다.

### 페이로드에 무엇을 넣는가

```ts
return new SignJWT({ typ: kind })
  .setSubject(userId).setIssuedAt().setExpirationTime(ttl).sign(key);
```

**토큰은 서명된 것이지 암호화된 것이 아니다.** 점으로 나뉜 세 조각 중 가운데는 base64url 로
인코딩된 JSON 일 뿐이라 jwt.io 에 붙여 넣으면 누구나 그대로 읽는다. 서명은 "고칠 수 없다" 를
보장하지 "못 읽는다" 를 보장하지 않는다. 그래서 이메일도 닉네임도 권한도 넣지 않는다.

발급된 액세스 토큰을 실제로 뜯어봤다. 점 2개로 나뉜 **192자** 문자열이고, 페이로드의 키는
`exp` · `iat` · `sub` · `typ` **넷뿐**, 이메일 문자열은 **0건**이다.

`typ` 만 우리가 넣은 값이다. 리프레시 토큰으로 API 를 부르지 못하게 막는 용도다 — 리프레시
토큰은 14일이라, 이것으로 API 를 부를 수 있으면 액세스 토큰을 15분으로 둔 의미가 사라진다.

### 만료와 서명 불일치를 같은 401 로 뭉갠다

`JWTExpired` 만 메시지를 따로 주고, 나머지는 전부 `UnauthenticatedError` 하나로 던진다. 둘 다
`401` `UNAUTHENTICATED` 이므로 **코드로 분기하는 프론트 입장에서는 같은 하나**이고, 그래야
"서명은 맞는데 만료다" 같은 힌트가 키를 맞춰 보는 쪽으로 새지 않는다.

401 이 나는 것 셋을 직접 호출해 확인했다 — **토큰 없음 · 만료된 토큰 · 남의 키로 서명한 토큰.**
서명 본문을 잘라낸 토큰도 401 이다.

### 실측에서 배운 것 — 서명 한 글자를 바꾸는 검사는 만들지 않는다

"서명을 한 글자 고치면 검증에 실패한다" 는 검사를 짰다가 실패했다. **base64url 서명의 마지막
글자는 비트를 2개만 담는다.** 나머지는 쓰이지 않으므로 마지막 글자를 바꿔도 **같은 32바이트로
디코드되어 검증을 통과한다.** 토큰이 뚫린 것이 아니라 검사를 잘못 짠 것이다. 위조 검사는
**서명 본문을 잘라내거나 남의 키로 서명하는 쪽**으로 짠다.

### 6.7 — 리프레시 토큰은 httpOnly 쿠키에 둔다

```ts
export const refreshCookieOptions = {
  httpOnly: true,
  sameSite: "strict" as const,
  secure: process.env.NODE_ENV === "production",
  path: "/auth",
  maxAge: 14 * 24 * 60 * 60 * 1000,
};
```

**`httpOnly` 대 localStorage** 가 이 블록의 전부다. localStorage 에 둔 토큰은 페이지에 끼어든
스크립트가 그냥 읽어 간다(XSS). `httpOnly` 쿠키는 자바스크립트가 아예 읽지 못하므로 그 경로가
막힌다. 대신 쿠키는 **요청에 자동으로 실려 가므로** 남의 사이트가 우리 API 를 부르게 만드는
공격(CSRF)이 열린다 — `sameSite: "strict"` 가 그 몫이고 `path: "/auth"` 도 같은 방향이다.
액세스 토큰을 15분으로 둔 이유도 같다. 결국 메모리나 localStorage 에 두게 되는데, 새어
나가도 15분 뒤에는 쓸모가 없다.

## 왜 이렇게 했는가

1. **서버가 리프레시 토큰을 저장하지 않는 것.** 검증에 서명 키만 있으면 되므로 DB 조회도
   테이블도 없다. 대가가 크다 — **발급한 토큰을 개별로 취소할 방법이 없다.** "이 기기만
   로그아웃" 도, 유출된 토큰 하나만 무효로 만드는 것도 안 된다. 서명 키를 바꿔 전원을
   한꺼번에 내보내는 것이 전부이고, 한계를 아는 채로 뒀다.
2. **세션이 아니라 JWT 인 것.** 세션이면 취소가 공짜다(서버 쪽 레코드를 지우면 끝). 대신
   요청마다 세션 저장소를 읽는다. JWT 를 고른 이유는 더 안전해서가 아니라 **"서명" 을 직접
   다뤄 보는 것이 6단계의 목표**라서다.
3. **`sign` 을 감추고 `signAccessToken` · `signRefreshToken` 만 내보낸 것.** 종류와 만료 시간이
   한 쌍으로 묶여 나간다. `sign(id, "access", "14d")` 같은 조합을 부를 자리를 없앤다.

## 직접 해 볼 것

1. 토큰을 점 기준으로 잘라 가운데 조각을 base64url 디코드한다 → 키가 넷뿐이다.
   `SignJWT({ typ: kind })` 에 이메일을 넣고 다시 디코드하면 무엇이 새는지 보인다. 되돌린다.
2. `jwtVerify` 의 `{ algorithms: [ALG] }` 를 지우고 헤더를 `alg: "none"` 으로 고친 토큰을 보낸다
   → 알고리즘을 값으로 못 박는 것이 무엇을 막고 있었는지 확인한다. 되돌린다.
3. 액세스 토큰을 `POST /auth/refresh` 의 쿠키 자리에 넣는다 → `typ` 검사에 걸려 `401` 이다.
   `if (payload.typ !== expected)` 를 지우면 통과한다. 14일과 15분의 구분이 이 한 줄에 있다.
