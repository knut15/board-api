# server/src/respond.ts

> 커리큘럼 2.4 · 3.6 · 짝: `server/src/respond.ts`

## 무엇을 하는 파일인가

에러 응답의 모양을 만드는 함수 하나가 들어 있다. `docs/02-api.md` 2.4 "에러 — 모든 4xx·5xx 가
이 형태 하나" 를 코드로 옮긴 것이다. 16줄인데 이 프로젝트에서 가장 많이 불리는 함수이고,
5단계에서 역할이 통째로 바뀐다.

## 코드를 따라 읽기

```ts
export function fail(
  res: Response, status: number, code: string, message: string,
  details: unknown = null,
) {
  res.status(status).json({ error: { code, message, details } });
}
```

`res.status(...)` 는 `res` 를 그대로 돌려주므로 `.json(...)` 을 이어 붙일 수 있다. 상태 코드와
바디를 한 줄에 쓰게 하는 것이 의도다 — 둘이 떨어져 있으면 `404` 를 쓰면서 성공 바디를 보내는
일이 생긴다.

`details` 의 기본값이 `null` 인 것은 명세에 맞추려는 것이다. 2.4 의 예시 JSON 에 `details` 키가
항상 있고, 검증 실패일 때만 `[{ "path": "title", "rule": "too_big" }]` 처럼 채운다. 기본값을
없애 키 자체를 빼면 프론트가 접근 전에 존재 검사를 해야 한다. **있으나 `null` 인 것과 없는
것은 다르다.**

호출하는 쪽은 이렇게 생겼다.

```ts
if (!post) {
  fail(res, 404, "POST_NOT_FOUND", "글을 찾을 수 없습니다.");
  return;
}
```

`return;` 이 꼭 필요하다. `fail()` 은 응답을 보내지만 **함수 실행을 멈추지는 않는다.** 빼면
아래 코드가 계속 돌고, 결국 이미 보낸 응답에 다시 쓰려는 상황이 된다. 프론트에서 `return` 을
빼먹으면 값이 이상해질 뿐이지만 여기서는 보낸 응답을 되돌리려 드는 셈이다. 5단계에서 `throw`
로 바뀌면 이 `return` 이 필요 없어진다 — `throw` 는 실행을 멈추기 때문이다.

`code` 의 타입이 `string` 인 것은 지금 일부러 느슨하게 둔 것이다. 오타가 나도 타입 검사를
통과한다. 2.4 의 에러 코드 목록 9개를 5.4 에서 상수로 옮길 때 좁혀진다.

## 왜 이렇게 했는가

1. **봉투를 한 곳에서 조립한 것.** 라우터마다 `res.status(404).json({ error: { … } })` 를 쓰는
   방법도 있다. 그러면 어디서는 `{ error: "..." }`, 어디서는 `{ message: "..." }` 가 되는 날이
   온다. 형태가 갈라지면 8.2 의 API 클라이언트가 분기를 여러 개 갖게 되고, 그 분기는 에러가 날
   때만 드러나 늦게 발견된다. 키를 고칠 자리가 한 군데라는 것이 이 파일의 값 전부다.
2. **성공 응답용 함수를 만들지 않은 것.** `ok(res, data)` 라는 짝이 대칭적으로 보이지만 성공
   응답은 `res.json(...)` 한 줄이고 상태 코드도 `200` · `201` · `204` 로 갈린다. 감쌀 것이 없는
   곳을 감싸면 읽는 사람이 함수 정의를 한 번 더 열어야 한다. 성공 바디의 *모양* 은 `views.ts` 가 맡는다.
3. **에러 클래스를 지금 안 만든 것.** `throw new NotFoundError()` 가 최종 모습이지만 3단계는
   함수 호출로 뒀다. 라우터가 어디서 어떤 코드를 내는지 눈으로 본 다음 예외로 옮기는 편이 덜
   헷갈린다고 봤다. 대신 지금은 `return` 을 빼먹을 여지가 남아 있다.

## 직접 해 볼 것

1. `routes/posts.ts` 의 `GET /posts/:id` 에서 `fail(...)` 다음 줄의 `return;` 을 지우고 없는
   id 로 호출한다 → 응답은 그대로 `404` 인데 서버 콘솔에 에러가 찍히는 것을 확인한다. 무슨
   에러인지 읽어 본다 — 없는 `post` 를 계속 쓰려 한 것과 이미 보낸 응답에 다시 쓰려 한 것이
   함께 드러난다.
2. `fail` 의 바디에서 `error` 를 없애 `{ code, message, details }` 로 바꾸고 아무 에러 응답을
   받는다 → 한 함수를 고쳐 11개 엔드포인트의 에러 형태가 전부 바뀌는 것을 확인한다. 2.4 와
   대조한 뒤 되돌린다.
3. `code` 파라미터 타입을 2.4 목록 9개의 유니언(`"POST_NOT_FOUND" | …`) 으로 좁히고
   `pnpm typecheck` 를 돌린다 → 목록에 없는 코드를 쓴 자리가 타입 에러로 드러난다. 5.4 가 이
   작업이다.

## 다음 단계에서 어떻게 바뀌는가

5.3 · 5.5 에서 `fail()` 호출이 `throw new AppError(404, "POST_NOT_FOUND", …)` 로 바뀐다.
라우터는 던지기만 하고 봉투 조립은 `app.ts` 의 에러 핸들러 하나가 맡으므로, 라우터가 `res` 를
넘겨받을 필요가 없어지는 것이 가장 큰 차이다. 5.4 에서 `code: string` 이 좁은 유니언이 되고,
5.2 의 검증 미들웨어가 zod 이슈를 2.3 의 선대로 `400` / `422` 로 가르며 `details` 를 채운다 —
라우터마다 손으로 넘기던 배열이 사라진다. 5.7 의 "내부 사정을 담지 않는다" 검사도 여기 붙는다.
