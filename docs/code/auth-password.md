# server/src/auth/password.ts

> 커리큘럼 6.1 · 짝: `server/src/auth/password.ts`

## 무엇을 하는 파일인가

비밀번호를 **되돌릴 수 없는 문자열로 바꾸고**, 나중에 들어온 평문이 그 문자열과 맞는지 답한다.
export 는 `hashPassword` 와 `verifyPassword` 둘뿐이고, 그 밖에는 아무것도 모른다 — DB 도
Express 도 import 하지 않는다.

5단계까지 `users` 테이블의 비밀번호 칸에는 평문이 그대로 들어 있었다. DB 덤프 한 번이면
가입자 전원의 비밀번호가 그대로 읽혔고, 같은 비밀번호를 다른 서비스에서도 쓰는 사람까지
같이 털렸다. 이 파일이 그 칸의 내용을 바꾼다.

## 코드를 따라 읽기

### 해시를 만드는 줄은 한 줄이다

```ts
export function hashPassword(plain: string): Promise<string> {
  return argon2.hash(plain);
}
```

옵션을 하나도 넘기지 않는다 — 라이브러리 기본값을 그대로 쓴다는 뜻이다. 이렇게 만든 해시를
실제로 찍어 보면 `$argon2id$v=19$m=65536,p=4,t=3$…` 로 시작하는 **97자** 문자열이다.

### 왜 SHA-256 한 번으로는 안 되는가

여기가 이 파일의 이유 전부다. SHA-256 은 **빠르라고 만든 함수**다. 빠르다는 것은 공격자에게도
빠르다는 뜻이라, GPU 한 장으로 흔한 비밀번호 후보를 전부 돌려 볼 수 있다. 사람이 고르는 짧은
문자열은 후보 목록이 생각보다 얇다.

게다가 **같은 입력은 언제나 같은 해시**다. 그래서 미리 계산해 둔 표(레인보우 테이블)를 조회만
하면 되고, 유출된 해시 목록 안에서 같은 값이 겹치면 "이 둘은 같은 비밀번호" 라는 사실까지
공짜로 드러난다.

argon2 는 정반대로 **느리고 메모리를 많이 쓰라고** 만들었다. 위 문자열의 `m=65536` 은 한 번
계산에 64MiB 를 쓴다는 뜻이고, `t=3` 은 3회 반복, `p=4` 는 병렬 4다. 메모리를 요구하면 GPU 에
수천 개를 동시에 얹기 어려워진다 — 속도가 아니라 **자원 요구량**으로 막는 것이다.

### salt 는 라이브러리가 넣는다

`argon2.hash` 는 부를 때마다 난수 salt 를 만들어 해시에 섞고, 그 salt 를 결과 문자열 안에
같이 넣는다. 그래서 같은 비밀번호라도 결과가 매번 다르고, 미리 만든 표가 통하지 않는다.

DB 를 열어 확인했다. `passwordHash` 가 전부 `$argon2id$` 로 시작하고, 평문 `password123` 은
**0건**이며, 같은 비밀번호로 만든 **두 계정의 해시가 서로 다르다.** 마지막 것이 salt 가 매번
다르다는 증거다.

### 파라미터가 해시 안에 들어 있다

`$argon2id$v=19$m=65536,p=4,t=3$<salt>$<hash>` — 알고리즘 · 버전 · 비용 파라미터 · salt 가
모두 한 문자열에 들어 있다. 검증할 때 이 값들을 읽어서 같은 조건으로 다시 계산하므로,
**나중에 비용을 올려도 옛 해시를 그대로 검증할 수 있다.** 하드웨어가 빨라져 `m` 을 두 배로
올리는 날이 와도, 이미 저장된 행을 한꺼번에 다시 만들 필요가 없다.

### `verify` 가 던지면 `false` 로 삼킨다

```ts
try {
  return await argon2.verify(hash, plain);
} catch {
  return false;
}
```

argon2 는 첫 인자가 자기 형식이 아니면 "틀렸다" 가 아니라 **예외**를 낸다. 6단계 전에 만들어진
평문 행이 정확히 그 경우다. 그대로 두면 예외가 에러 핸들러까지 올라가 `500` 이 나가는데,
로그인 실패는 `401` `INVALID_CREDENTIALS` 여야 한다(`docs/02-api.md` 2.4). 형식이 아닌 것은
**통과시키지 않는다**는 뜻이므로 `false` 가 맞다.

## 왜 이렇게 했는가

1. **비용 파라미터를 손으로 정하지 않은 것.** 기기 성능에 맞춰 `m` · `t` 를 재 보고 고정하는
   방법도 있다. 그러면 이 프로젝트가 도는 어느 기기에서 잰 값인지가 코드에 박히고, 배포
   환경이 바뀌면 다시 재야 한다. 기본값을 쓰면 라이브러리가 권장값을 올릴 때 같이 올라간다.
   대신 "우리 서버에서 로그인 한 번에 몇 ms" 를 우리가 고른 것은 아니게 된다.
2. **bcrypt 가 아니라 argon2 인 것.** bcrypt 도 일부러 느리지만 메모리를 거의 쓰지 않아,
   막는 수단이 사실상 반복 횟수 하나다. argon2id 는 메모리까지 요구해 전용 하드웨어에 더
   버틴다. 대가는 의존성이다 — argon2 는 네이티브 모듈이라 순수 JS 구현보다 설치가 무겁다.
3. **`verifyPassword(hash, plain)` 인자 순서.** `argon2.verify` 와 같은 순서로 맞췄다. 둘을
   반대로 두면 이 파일 안에서 뒤집어야 하고, 뒤집는 자리가 생기면 언젠가 잘못 뒤집는다.
   두 인자가 모두 `string` 이라 타입이 잡아 주지 못하는 자리이기도 하다.

## 직접 해 볼 것

1. `hashPassword("같은값")` 을 두 번 불러 결과를 비교한다 → 두 문자열이 다르다. 그런데 각각을
   `verifyPassword` 에 넣으면 둘 다 `true` 다. salt 가 무엇을 하는지 한 번에 보인다.
2. `verifyPassword("password123", "password123")` 를 부른다 → 해시 형식이 아니라 argon2 가
   던지고, `catch` 가 `false` 로 바꾼다. `catch` 블록을 잠시 지우고 같은 호출을 하면 예외가
   그대로 올라간다. 평문 행이 남아 있을 때 로그인이 `500` 이 되는 경로다. 되돌린다.
3. 가입 요청을 보낸 뒤 `pnpm db:psql` 로 `passwordHash` 를 직접 본다 → `$argon2id$` 로 시작하고
   평문이 어디에도 없다. `routes/auth.ts` 에서 평문이 `hashPassword` 아래로 내려가지 않는다는
   것을 눈으로 확인하는 절차다.
